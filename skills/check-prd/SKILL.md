# check-prd

对 B端 PRD 或系统设计文档进行严格、可执行的质量审查。

支持显式调用（如 `/check-prd path/to/prd.pdf`）和自动触发（当用户明确要求审查 PRD、需求文档、产品方案或企业系统设计时）。

## 输入

- 通过 `$ARGUMENTS` 传入的文件路径
- 或用户粘贴的 PRD / 系统设计文档内容
- 或不完整的文档（基于现有内容审查，并明确指出缺失的上下文）

如有参数传入，优先作为输入源：

$ARGUMENTS

## 审查前的准备

先识别用户要报告还是修订。只审查时不改原文；已要求修改时，完成聚焦审查后按 `../create-prd/SKILL.md` 的相应范围修订并核对，不另开一轮批准或强制整份重写。无法查明的业务决定保留为待决，其他已授权修订继续。

1. 完整阅读文档后再对各维度进行评判。
2. 确定并记录：
   - 商业属性：自研内部系统 or 商业化产品
   - 功能类型：业务型管理软件 / 工具型软件 / 交易型平台 / 基础服务型
   - 文档范围：0-1 完整系统 / 系统级重构或大版本 / 模块级迭代 / 单点功能变更 / 快速产品说明
   - 审查强度：完整严格审查 / 聚焦审查 / 轻量审查
   - 是否涉及 AI 功能
3. 在开始逐维度审查前，标记不适用的维度和降低要求的维度。

### 审查强度分支

| 文档范围 | 审查强度 | 审查方式 |
| --- | --- | --- |
| 0-1 完整系统 | 完整严格审查 | 执行 14 个维度，按复杂 B 端系统标准判断完整性 |
| 系统级重构或大版本 | 完整严格审查 | 执行 14 个维度，重点增加迁移、兼容、灰度、历史数据和新旧流程差异 |
| 模块级迭代 | 聚焦审查 | 重点审查 04 场景、05 结构、07 局部数据、08 流程/状态/权限、09 交互、12 异常、验收口径；商业、架构、运营按影响范围降低要求 |
| 单点功能变更 | 轻量审查 | 重点审查问题目标、影响范围、入口页面、字段/按钮/规则、状态差异、权限差异、异常兼容、验收标准 |
| 快速产品说明 | 轻量审查 | 只检查目标、范围、关键规则、验收和待决事项是否能支撑沟通与执行 |

### 降低标准原则

- 对模块级迭代、单点功能变更、快速产品说明，不得因为缺少完整 14 章、完整商业分析、完整系统架构图、完整 ER 图、完整运营计划而直接判定为“严重缺失”。
- 降低标准不等于放松关键实现信息。凡是影响研发、测试、权限、数据、状态、兼容和上线风险的信息，仍应严格检查。
- 对已有系统的局部变更，优先判断“是否足以支撑本次迭代开发和验收”，而不是“是否像 0-1 系统设计一样完整”。
- 涉及有状态实体时，无论文档范围大小，都要检查不同状态下字段和操作的可见、可编辑、可触发规则。

### 适用性规则

| 维度 | 适用条件 | 不适用时处理 |
| --- | --- | --- |
| 07-数据建模 | 仅业务型管理软件和交易型平台 | 标注"不适用"，仅检查关键数据结构 |
| 10-商业分析 | 仅商业化产品 | 自研内部系统只检查投入产出分析 |
| 03-竞品分析子项 | 仅商业化产品 | 自研内部系统改为同类系统参考 |
| 06-企业架构层 6.5-6.9 | 仅 0-1 新系统设计或系统级规划 | 迭代需求只做 6.1-6.4 |
| R8-多租户风险项 | 仅商业化 SaaS 产品 | 标注"不适用" |
| 13-AI 功能 | 仅文档涉及 AI 功能 | 标注"不适用" |
| 完整14章结构 | 仅 0-1 完整系统、系统级重构或大版本 | 模块级/单点需求按其分支结构检查 |
| 完整ER图 | 仅核心数据模型变化、0-1完整系统、交易闭环变化 | 轻量需求只检查受影响字段和局部数据关系 |
| 完整运营计划 | 仅商业化产品上线、重大系统推广、流程变更影响大量用户 | 单点功能只检查发布说明、培训或通知是否必要 |

## 输出规范

### 不可违反的行为规则

- 按当前文档范围覆盖适用维度；顺序可以随风险和依赖调整，不为轻量请求执行全套维度。
- 默认汇总后交付一份报告；用户要求逐维度审看时才分段交付，长审查用简短进展说明保持沟通。
- 同一根因跨维度出现时合并报告，保留各受影响位置，不重复计算问题。
- 每条发现必须指向 PRD 中的具体位置，或明确说明缺少相关证据。

### 每个维度的输出格式

```md
## 维度[编号] - [名称] ｜ 评级：[优秀 / 合格 / 待改进 / 严重缺失]

### 具体发现

**发现 1：[问题标题]** [P0/P1/P2/P3]
- PRD定位：第X节/[功能名称]
- 问题描述：[具体说明问题，不要泛泛而谈]
- 改进示例：[给出可以立刻执行的改法]

### 隐性问题推断
结合产品类型和业务场景，列出 PRD 没写但按道理必须考虑的问题。
```

### 最低质量标准

- 完整严格审查：覆盖每个适用维度，发现数量由证据决定；没有问题时简述已检查边界，不凑满固定条数。
- 聚焦审查：覆盖本次重点维度，其他维度按影响判断；不为显得完整而添加推测性缺陷。
- 轻量审查：围绕影响范围、字段规则、状态权限、异常兼容、验收标准输出核心发现，不强制每个维度凑满 3 条。
- 发现必须锚定到 PRD 中的真实章节、流程、页面或字段。
- 建议必须可执行，不得笼统模糊。
- 对于维度 09（交互设计），逐一检查文档中描述的每个页面、弹窗、表单和关键操作，明确指出缺失的交互细节。
- 对于有状态实体，必须检查是否说明“状态 × 字段/操作 × 角色”的可见、可编辑、可触发规则；缺失时按影响程度标为 P0/P1/P2。

## 最终报告要求

完成适用范围后，生成一份可独立阅读的报告，按实际发现包含：

1. 产品定型说明
2. 各维度发现摘要
3. 重大风险项
4. 按 P0-P3 排序的问题清单
5. 亮点记录
6. 按影响排序的改进建议，数量以真实问题为准

报告直接包含判断所需的证据与改法；长篇细节可放附录，不要求先逐维度输出全文再重复汇总。已要求修订时，同时交付修改后的文档与尚待用户决定的事项。

## 工作风格

- 目标是发现盲区、改进文档，不是给作者难堪。
- 对证据和具体性保持严格要求。
- 根据产品类型、产品阶段和文档范围调整判断标准。
- 如果文档不完整，说明哪些内容无法验证，然后基于现有证据继续审查。
