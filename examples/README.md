# 使用示例

以下输入均为虚构场景，可以直接改写后在 Codex 中使用。它们用于展示如何给 Skill 足够上下文，不是标准答案。

## 创建：模块级迭代

```text
我们要在连锁门店后台增加设备报修模块。

角色：店员、店长、平台运营、维修服务商。
主流程：店员提交故障和图片，店长确认，平台派单，维修商接单并反馈结果，店长验收。
已知约束：同一设备同时只能有一个处理中工单；超过 24 小时未接单需要提醒平台运营。

请先判断产品类型和文档范围，确认后生成模块迭代 PRD。重点写清工单状态、不同角色可执行操作、超时异常和验收标准；未知信息用 TODO 标记。
```

预期行为：识别为已有企业系统中的业务模块，不机械补齐商业分析和完整系统架构；对工单状态、字段可编辑性和角色权限保持严格。

## 创建：单点功能变更

```text
现有采购单列表要增加“批量导出”操作。

只有采购管理员可见；一次最多选择 500 条；导出任务在后台执行，完成后通知发起人；失败任务可重试一次。请生成单点功能 PRD，并列出还需要业务确认的问题。
```

预期行为：使用轻量结构，覆盖入口、选择规则、权限、异步任务状态、失败重试、通知和验收，不扩写无关的市场或运营章节。

## 审查：状态与权限

```text
请审查 docs/purchase-approval-prd.md。

这是已有采购系统的审批模块改造。重点检查：
1. 申请单在草稿、审批中、已通过、已驳回、已撤回状态下哪些字段可以编辑；
2. 申请人、直属主管、财务和管理员分别能执行什么操作；
3. 加签、转交、撤回和重复提交的异常路径；
4. 验收标准是否足以让测试直接编写用例。
```

预期行为：问题锚定到原文或明确缺失证据，按 P0–P3 排序，并给出可以直接补进 PRD 的规则示例。

## 审查：AI 功能

```text
请审查一个客服工单摘要功能的 PRD。模型会读取会话并生成摘要、问题分类和建议回复，客服确认后才能写入工单。

除常规流程外，重点检查最小上下文、敏感信息、幻觉、人工确认、失败降级、模型评估和成本监控。
```

预期行为：启用 AI 功能审查维度；不只评价 Prompt，还检查数据边界、人在回路、质量评估、失败恢复和运营监控。

## 提供上下文的小技巧

- 说明这是 0-1 系统、模块迭代还是单点变更；不确定时让 Skill 先判断。
- 提供真实的角色、状态、核心对象和业务约束，比提供“写得专业一点”更有效。
- 明确哪些是已确认事实，哪些是假设，哪些必须保留为待决。
- 审查时指出最担心的风险，但允许 Skill 继续检查相邻的高影响问题。
