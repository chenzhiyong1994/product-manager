WHY PRODUCTMANAGER

文档不是越长越专业，
而是越能支撑行动越有价值。

小改动不需要十四章仪式感，复杂系统也不能把状态、权限和异常藏在漂亮文案后面。

01

拒绝模板绑架

先识别完整系统、模块迭代还是单点变更，再匹配内容深度。

02

拒绝无证据批评

每条发现都指向章节、页面、字段、流程或明确缺口，并给出可执行改法。

03

保留真实未知

没有业务证据的事实继续标记为 [TODO]，不让合理化想象进入契约。

01 / CREATE create-prd

从散乱上下文，生成范围匹配的 PRD。

识别商业属性、功能类型与文档范围，只加载当前任务需要的规则。

scope-router

input 连锁门店设备报修模块

type 业务型管理软件

scope 模块级迭代

output 9 节聚焦结构 + 明确缺口

02 / REVIEW check-prd

从“看起来完整”，审查到真正可交付。

按适用维度检查证据，以 P0–P3 标记影响，而不是机械凑问题数量。

P2超时路径缺少负责人第 7 节 · 异常处理待补充
✓验收口径可测试第 8 节 · 验收标准通过

HOW IT WORKS

不是万能 Prompt，
是一条可维护的决策链。

稳定规则留在 Skill，细节按任务需要从 references 渐进加载。范围变化，工作深度随之变化。

  1. 01输入业务上下文想法、纪要、现有 PRD
  2. 02识别产品与范围商业属性、功能类型、文档级别
  3. 03加载适用规则章节、维度、风险与示例
  4. 04交付并验证可执行内容、证据与明确缺口
PROMPT LAB

一句自然语言，进入正确的工作流。

无需记命令。描述你真正想完成的事情，项目级路由会选择对应 Skill。

codex / product-manager● ready
我们要给连锁门店做一个设备报修模块，店员提交、店长确认、维修商处理。请写一份模块迭代 PRD。
ROUTED TO create-prd · 模块级迭代

输出聚焦流程、状态、角色权限、字段规则、异常与验收；未知业务事实保留为待决。

SCOPE-AWARE

同一个标准，不该压在所有需求上。

ProductManager 按实际范围选择结构与审查强度，让文档成本与决策风险相匹配。

01

0–1 完整系统

完整 14 章，覆盖架构、数据、流程、权限、运营。

FULL PRD
02

系统重构 / 大版本

强化迁移、兼容、灰度、历史数据和新旧流程。

STRICT REVIEW
03

模块级迭代

9 节聚焦结构，围绕受影响模块讲清可实施规则。

FOCUSED
04

LIGHTWEIGHT
05
